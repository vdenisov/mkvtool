# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A Kotlin/JVM command-line tool for automating MKV workflows — primarily TV show episodes. One binary,
`mkvtool`, with nine subcommands, built with Gradle and shipped as GraalVM native-image binaries per OS
plus a fat jar as the JVM fallback.

It began as nine separate Groovy scripts. They are still in the tree and still work, frozen, until they
are deleted; what that era left behind that still shapes the code is in the last section.

**Documentation layers.** `README.md` is the front gate — install, the subcommand tour, a minimal config
quick-start. User-facing depth (output and colour conventions, the check-report reading guide, the full
`config.yaml` field reference) lives in `docs/reference.md`. This file holds implementation internals.
When adding documentation, put it in the right layer instead of growing the README.

Planning and design documents (direction, porting plan, workflow expansion, distribution, backlog) exist
in the working tree but are **untracked**, and nothing tracked may reference them: code, comments, commit
messages and PR descriptions have to be self-contained, because a reader of the repository cannot see
those files. Say the thing, do not cite the plan.

## Running it

Every command operates on the current working directory — in practice the directory holding the media
files. The dev loop:

```bash
./gradlew installDist        # build/install/mkvtool/bin/mkvtool[.bat]
./gradlew shadowJar          # build/libs/mkvtool-<version>-all.jar
./gradlew nativeCompile      # build/native/nativeCompile/mkvtool[.exe]; needs a GraalVM JDK 21
./gradlew build              # compile + unit tests + the fat jar
./gradlew jarLauncher        # build/jar-launcher/mkvtool[.bat] — runs the fat jar
./gradlew releaseArchive     # build/release/mkvtool-<version>-<os>-<arch>.{zip,tar.gz}
```

Subcommands: `mux`, `inspect`, `fetch-episodes`, `rename`, `filename-to-title`, `propedit`, `to-utf8`,
`fix-srt`, `find-unused-fonts`, plus the hidden `native-smoke` build probe. The user-facing tour is in
`README.md`; the option surface is in the `@Command` classes under `cli/`.

`mux` reads `config.yaml` from the CWD (a per-show config next to the media files) or from an explicit
`--config <path>`. There is **no** fallback to a config anywhere else, and the shipped
`config.example.yaml` is never auto-loaded: silently applying a demo config's track selections to an
unrelated directory produced confidently wrong output, and the giveaway was a wrong `config title` on a
check verdict. A muxing run with no config is a clean exit-2 error naming the template, never a stack
trace.

**Inspection lives in `inspect`, not in `mux`.** A config is optional in one and required in the other,
and those two personalities used to share a script; separate entry points are the fix.

## Build

- Gradle with the Kotlin DSL, single project, packages rather than modules. **Every version — project,
  dependencies, plugins — lives only in `gradle.properties`**; build scripts and code read it from there.
  Do not inline a version anywhere else.
- **JDK 21 toolchain and a JDK 21 target, deliberately.** Both stay on 21 as newer JDKs appear; do not
  raise the target. The Gradle version itself is unconstrained.
- picocli for the CLI, with `picocli-codegen` run through **kapt** — it is a javac annotation processor,
  so KSP cannot run it — emitting the GraalVM reflection config under `META-INF/native-image`. Prefer no
  runtime reflection at all; anything new that needs it needs codegen coverage or explicit config.
- `kotlinx-serialization-json` for JSON (`mkvmerge -J` today, TheMovieDB, and `--json` output later). It
  is a *compiler* plugin, so serializers are generated at compile time and need no reachability config.
- snakeyaml for `config.yaml` and `episodes.yaml`, **safe-load only**, mapped manually into typed models.
  No reflection-based data binding: it fights native-image and cannot reproduce the lenient
  classification semantics the loaders need.
- `BuildInfo.kt` is generated by the `generateBuildInfo` task and holds the version as a compiled-in
  `const`, so `--version` needs no classpath resource — one less thing to tell native-image about.
- The shadow plugin produces the fat jar; the application plugin names the `installDist` launcher
  `mkvtool`.

### Release packaging

Four tasks, all in the build rather than in workflow shell — one task writes the same archive on three
hosts (the Windows runner's Git Bash has no `zip`), the tar entry's executable bit is *set* rather than
inherited from the filesystem, and the whole thing runs on a developer machine before it is pushed.

- `releaseArchive` — the flat per-platform archive: the bare binary renamed to `mkvtool`/`mkvtool.exe`
  (that inner name is what a Scoop `bin` and a Homebrew `bin.install` point at), `LICENSE`, and the
  `README.txt` that `releaseReadme` renders from one template with a per-OS paragraph. Two properties are
  load-bearing. The **platform label is derived from the host**, never passed in: a passed label can lie,
  so a toolchain mix-up would mislabel an architecture, while a derived one makes two CI legs collide on
  one file name and fail the asset check instead. And it **does not depend on `nativeCompile`** — it
  archives the binary as it stands, which in CI is the one that was just smoke-tested; a fresh compile
  would be an untested one. `-PnativeBinary=<path>` points it at a binary from elsewhere, which is how an
  archive is rebuilt around a signed exe.
- `releaseJar` — the shadow jar under its release name. A copy, not a reclassified `shadowJar`, because
  the thin `jar` task already owns `build/libs/mkvtool-<version>.jar`.
- `printVersion` — how CI learns the version, so nothing parses `gradle.properties` as a second
  implementation of the single source of truth.
- `jarLauncher` — see Testing: the fat jar's only way into the acceptance harness.

### Native image

Three build args, each guarding a failure mode that is **silent** on an ordinary JVM:

- `-H:+AddAllCharsets` — without it `to-utf8` loses every non-default encoding and `Charset.forName`
  throws.
- `-H:+IncludeAllLocales` — without it CLDR display names come back empty, so language names and the
  language guesser quietly stop working.
- `--initialize-at-build-time=kotlin.DeprecationLevel` — kotlinx-serialization's generated serializers
  initialize at build time and reach that enum, which native-image's default policy wants at run time;
  the disagreement fails `nativeCompile` outright as soon as anything `@Serializable` is reachable.

The plugin's **reachability-metadata repository is disabled**. The last GraalVM CE for JDK 21 is 21.0.2,
and native-build-tools' metadata schema demands a newer GraalVM than that ships, so leaving it enabled
fails the build on every OS. Our only reachability config comes from picocli-codegen, and picocli ships
its own. Re-enabling it would mean moving off community-21 — a distribution decision, not a flip.

**No `\u` sequence in any comment.** kapt generates Java stubs and javac decodes unicode escapes *before*
stripping comments, so a comment mentioning a numeric escape fails the build in a generated file nobody
wrote. Say "a numeric escape" in words.

## Layout and layering

```
org.plukh.mkvtool.core        — the domain: one engine per command plus the internals they sit on
org.plukh.mkvtool.cli         — picocli commands, option parsing, exit codes
org.plukh.mkvtool.cli.render  — the text renderers and the type→renderer binding table
org.plukh.mkvtool.out         — the output seam: diagnostics events, renderers, the registry, the palette
```

Dependencies run **`out` ← `core` ← `cli`**, and `out` never names a core result type — that is what
keeps the seam acyclic while `core` still emits through it.

Helpers are ordinary functions and classes. The script era's disciplines — closures instead of methods,
declaration ordering, injected parsers instead of imports — were workarounds for the delivery mechanism
and must not be replicated. Keep the seams that encode *semantics* (the caller does I/O, the helper owns
meaning: `normalizeYaml` takes an already-parsed map, `trackVarsFor` takes an already-probed track,
`buildCheckReport` takes an `externalsOf` lookup), and drop the ones that only encoded the no-imports
rule.

**Explicit charsets on every read and write.** Where behaviour deliberately auto-detects — a
hand-assembled `episodes.txt` — use `core/CharsetDetection.kt` rather than quietly forcing UTF-8.

## Testing

Three tiers, answering different questions.

**Unit (Kotest, `src/test/kotlin`).** In-process, fast, **no mkvmerge and no subprocess** — probe results
are faked data. That contract is deliberate; keep it. Data-driven tables for anything with more than two
cases. Shared doubles live beside the tests: `SilentRenderer`, `RecordingRenderer`, `ProbeFixtures`,
`RenderCapture`.

**Acceptance (`src/test/run_tests.groovy`, 132 cases).** The oracle the port was built against, and the
only end-to-end coverage in the project: it runs the real thing as a subprocess against real MKV fixtures
and asserts via `mkvmerge -J`. `--target app` runs the binary (the default is `scripts`), and
`--app-bin`/`MKVTOOL_APP_BIN` points it at any binary — the native one included.

It is **frozen**: do not edit it, and treat a red case as a bug in the code rather than in the test.
Assertions are substring `contains(...)` checks, so output has to reproduce the pinned text closely enough
that every substring holds — including the `*** Error: ` / `*** Warning: ` prefixes, the stdout/stderr
routing and the exit codes.

Harness conventions worth knowing before touching anything it covers:

- Fixtures derive from one input, `src/test/test.mkv`: track 0 video (und), 1–3 audio (jpn/eng/rus), 4–6
  subtitles (eng/rus-forced/jpn). `buildVariant` derives an MKV with a chosen track subset and per-id
  overrides — and **mkvmerge renumbers surviving tracks from 0 in source order**, so a variant's ids are
  not the source ids unless all tracks are kept, while `--track-name` still targets the *source* id.
  Getting that wrong leaves a name silently unchanged.
- Cases needing `mkvpropedit`, a bare `groovy` on `PATH`, or a TheMovieDB key skip themselves with a
  printed note rather than failing.
- `withStubServer` serves canned JSON from a JDK `HttpServer`, which is how `fetch-episodes` is tested
  offline through its hidden `--base-url`.
- **Never run two suites at once**, a `--filter` run alongside a full one included: work directories are
  keyed by case name and recreated at case start, so a second run wipes the first one's fixtures mid-test
  and the failure surfaces somewhere unrelated to what is being worked on.

**Native smoke (`mkvtool native-smoke`, hidden).** Seven self-asserting probes — a windows-1251 decode, a
CLDR native name, a real language guess, a JSON parse, a snakeyaml load and a dump, and an HTTPS request
against a dead loopback port — comparing values *inside* the runtime, so CI only has to check the exit
code. Each one covers something that fails silently in a misconfigured native image. It needs no network
and no external tool.

**The fat jar** gets a fourth, smaller pass, in the same CI job as the JVM launcher: `--version`,
`native-smoke`, and three harness cases through the launcher `jarLauncher` generates. It is the published
JVM fallback, and what only *it* can break is its own packaging — the `Main-Class` manifest and the
resources merged from several dependencies — which is most of what `native-smoke` probes anyway. The full
132 would add minutes to re-run bytecode that job has already run through `installDist`. The launcher is
generated rather than committed because it has to name the versioned jar, and because the harness needs an
executable to point `--app-bin` at: hence a shebang and the executable bit on POSIX, a `.bat` on Windows
(the harness routes those through `cmd /c` and launches anything else directly), argv forwarded, the exit
code passed through, nothing of its own printed, and the jar addressed relative to the script, since each
case runs in a fresh working directory.

CI runs the unit tier and both JVM acceptance tiers on every push and PR; a 4-OS native leg (compile, the
smoke probes, the acceptance suite in full on Linux and a representative case per command elsewhere, a
`--version` startup measurement asserted under 200 ms, and the release archive for that platform) on
merge, a pushed `v*` tag, a weekly schedule and manual dispatch; and the live TheMovieDB contract case on
the schedule only, so network flakiness cannot redden the badge.

**Releases never publish from CI.** A pushed `v*` tag collects the four archives, the jar and a
`sha256sum` checksums file, asserts the asset set and each archive's shape against the naming contract,
and creates a **draft**; a dispatch does everything except that last call and leaves the assets as a
workflow artifact, which is how the path is rehearsed without spending a tag. The Windows binary **ships
unsigned** for now, and the install instructions say so rather than promising a signature. Two consequences
worth knowing: the Windows leg uploads the bare exe on its own, so a signature can later be appended to the
binary that was actually tested rather than to a local rebuild; and a published asset is never re-signed in
place — the next version gets the signature, because anything that pinned the old checksum would start
failing.

## The output seam

Two layers, following the mkvmerge precedent: its text output and its `-J` output are two projections of
one model, the text is lossy, and the JSON cannot be reconstructed from it. So text and JSON both derive
from a model, and no stream of composed lines is ever the seam.

**Results — what a command computes.** A typed model: dumb data, no logic, no self-presentation, field
names describing domain meaning and never rendering (`differing`, `guessed`, `secondary`, never
`grayed`). Nested operations produce nested results that the parent composes; the parent owns its
document and may embed a child verbatim, filter it, or derive an entirely new shape from it, while a child
returns its full natural answer and never knows any parent's contract — which is what keeps children
reusable. Every result carries its own identity as fields, so meaning never rides on emission order. The
root is also the core function's return value, and unit tests assert on it with no renderer involved. A
command's document shape stays stable across flags: prefer compute-gating or presentation-filtering over
reshaping the model per flag.

**Diagnostics — what a command says while working.** Errors, warnings, narration and progress, as
message-shaped `OutputEvent`s rendered on arrival. The one hard rule: **no result data travels over
diagnostics.** Composing a finding or an outcome into a message string inside command logic is exactly the
move that destroys the structure JSON needs.

**Emission is the command's choice; presentation is the type's.** What appears is decided by what a
command emits — children as they complete, the root alone, or both — while how each one looks is fixed by
its type's renderer, identically in every command. Emitting both is legitimate only when the root's
rendering is the parent's own projection (a summary line), never the children a second time. A root may be
returned and never emitted at all: `InspectReport` is the future `--json` document, but the command prints
no batch summary — the children *are* the output — so it is deliberately absent from the binding table.

**One medium, one binding table.** The medium is chosen in exactly one place, `cli/OutputOptions` (the
mixin that also carries `--color`), so `--json` is a flag there and a branch in one method rather than an
edit in nine commands. Which renderer draws a given result type is decided in exactly one table,
`cli/render/TextResultRenderers.kt`, a registry of typed leaves. Lookup is by **exact class** — a
supertype walk would need `kotlin-reflect`, which native-image does without — so every concrete result
type registers itself or fails loudly on first emission. Renderers are named for the data they draw, never
for a command, because the same renderer serves every command emitting that type. `out/RenderHints.kt` is
the only channel by which a command may tune presentation, and its whole vocabulary today is
`verboseFileLists`.

**Renderers project, never compute.** A parent may change *what* the answer is; a renderer only changes
how much of it you see and how it looks. All human message text is composed in renderers — command logic
never pre-composes prose.

The palette, its gating and the shared message forms live in `out/TextRenderer.kt`: red errors, green
success, yellow warnings and the differing-cell highlight, cyan headers, gray de-emphasis; `always`, or
`auto` on a terminal without `NO_COLOR`, else `never`; `*** Error: `/`*** Warning: ` to **stderr** and the
rest to stdout. Three details are load-bearing:

- **Escapes wrap whole lines or whole pre-padded table cells, never a fragment inside a phrase.** The
  suite asserts on substrings, so a mid-phrase escape breaks tests and reads as flicker anyway; padding
  before colour is what keeps tables aligned. The sanctioned exceptions are two-segment lines whose
  segments each stay contiguous: the check report's `<-` marker row, and `inspect`'s external block header.
- **Counts are spelled out properly** — no `file(s)` anywhere. Every count knows its own number, so the
  form-letter `(s)` buys nothing and costs readability. `plural`/`pluralize` are pure functions in `out`;
  they build message text, not output.
- **A multi-line hint is printed line by line.** One `println` of the whole string leaves every line but
  the last with a bare `\n` while the last gets the platform separator — mixed endings in any redirected
  log on Windows, visible only byte for byte.

The progress meter renders an in-place bar on a terminal and appended dots anywhere else, because `\r`
erases nothing in a pipe and every frame would be retained. Dots are emitted per slice of the total, so a
200-file batch cannot wrap the terminal.

**No terminal or ANSI library.** Hand-rolled escapes: a library's opinions about reset sequences, style
composition and width-aware padding (`日本語` pads differently than `String` length does) are all output
drift.

## Commands and cores

Each command gets its own core, result model and renderer, and sharing is limited to **pure helpers**.
`filename-to-title` and `propedit` have a byte-identical loop and were still built as two of everything:
each result model is that command's `--json` document, and `propedit` has no title to report, so one
shared shape could not be domain-complete for both. Duplicate the loop, not the model.

The exception, and the reason it is one: the consistency report has a single renderer shared by `inspect`
and `mux`, because the report *must* look identical in both, and a second copy would be a drift bug
waiting to happen. `headerLabel` rides on the model (`Consistency check` versus `Pre-flight check`) and is
the only difference; `verbose` is a renderer setting, not a model field.

## Behavioural contracts

These describe the *tool* and are the specification. Where one looks arbitrary, it is load-bearing.

### Exit codes

Every batch command exits non-zero if any file failed, so all are usable from a shell script. Environment
and setup errors exit 2 before touching anything: an unusable `--encoding`, a missing mkvpropedit, an
unusable config. `fetch-episodes` exits 2 on API-key problems and 3 on network or API failures. `mux`
keeps continue-on-error and **always exits 0** — a partially successful batch mux is a normal outcome —
except under `--strict`, which exits 2 when a discrepancy affects a selected track. `inspect` writes
nothing and **exits 0 whatever it finds**; `--strict` is its only non-zero path, a `--config` path that
does not exist very much included (it warns and carries on, because a stale config must never stand
between the user and the track table, least of all when reading that table is how they would fix it).

### Episode metadata: `episodes.yaml` and `episodes.txt`

`fetch-episodes` writes **both, always**, and **neither is sanitized** — names carry the exact TheMovieDB
spelling, `:` and `?` included. Stripping happens in `rename`, at the point a name becomes a file name,
because `mux` needs the original spelling for `${episodeName}` and a name stripped at fetch time could
never be recovered.

`episodes.yaml` carries show name, year, season number and name, the fetch locale, and every episode by
its **real** `episode_number`, so a gap in a season does not shift everything after it. `episodes.txt`
stays the format that can be written by hand — one name per line, matched by line order plus
`episodeOffset`. Both `rename` and `mux` prefer the yaml.

**`episodeOffset` applies to `episodes.txt` alone.** That file has no numbers in it, so the offset is part
of *how it is read*: it is the episode number of the first line, which is what makes a partial file
(titles for E11–E20) usable. The yaml carries real numbers, so nothing is shifted and the offset is
ignored there. Anyone wanting genuine renumbering — anime absolute numbering against a season-split show —
needs an explicitly named option for it rather than a second meaning on this one.

`mux` reads `episodes.txt` as line N = episode N and takes no offset: it is not the command that decides
numbering. A trimmed file therefore misses, and the stage-two pre-flight reports those files as dropped
rather than stamping a wrong title into them. The alternative — sorting the files and matching
positionally — fails the other way round, silently mis-titling when the file holds a full season and only
some episodes are present. **Missing loudly beats mis-titling quietly.**

Both files are hand-editable, so **every reader guards them** exactly as it guards `config.yaml`: a syntax
error, a top-level list, an empty file, or an episode number that is not a number. All load sites go
through `loadMapping`, which *classifies* and nothing more; the policy stays with each caller. `mux` exits
2 on any problem in either file, because a title stamped from metadata it could not read is the same
confidently-wrong output as a mux against a config it did not understand. `inspect` warns and continues,
and counts only `config.yaml` into its problem count — `--strict` means "treat the findings as a failure",
and episode metadata produces no findings; it only decorates the source paths `--identify` resolves.
`normalizeYaml` runs *inside* the guard, as `loadMapping`'s transform, because `episode: "one"` throws
there rather than at parse time.

Charset contract: the yaml is read and written with an **explicit UTF-8** both ways — it is
machine-written, so it is a fixed contract — and dumped with `allowUnicode`, without which snakeyaml
escapes every Cyrillic character and produces valid YAML that is unreadable for exactly the titles the
feature exists to preserve. `episodes.txt` is read with **auto-detection on purpose**, since forcing UTF-8
would break a hand-assembled file and gains nothing.

### `config.yaml`

The per-directory config is the load-bearing decision: all track selections live in a reviewable,
hand-editable file next to the media, so you can diff it, keep it beside the season forever, and re-run
the mux in five years.

Reading it is **lenient**: a field of the wrong shape comes back absent rather than throwing, because a
config is optional throughout `inspect`. Ids are coerced, so a quoted `id: "2"` still selects track 2. One
distinction is not lenient and must not be flattened: **a declared template is not an absent one.** A
missing key leaves the field's default (the file name); a key written with no value is a *declared* empty
template and overrides that default. It is load-bearing in both the validation and the command line.

`trackOrder` is derived from the configured tracks when omitted (video, audio in listed order, subtitles,
then one entry per additional source). When set explicitly it is validated and mismatches are **warned
about, never fatal** — mkvmerge itself silently ignores entries matching no muxed track, so a stale id
left behind after editing the track lists would otherwise have no visible effect at all.

Omitting `audioTracks` or `subtitleTracks` (or setting them to `[]`) copies no tracks of that type.

| Field | Purpose |
|-------|---------|
| `general.mkvmergeExe` | Optional full path; omit to auto-detect from PATH, with a Windows default-location fallback |
| `general.destinationDir` | Output folder, relative to the CWD |
| `general.title` | Optional segment (container) title, templated; distinct from `mainSource.videoTrack.title`, and each defaults to the file name independently |
| `general.allowedExtensions` | Which file types count as main sources |
| `mainSource.videoTrack` | Language and optional title override |
| `mainSource.audioTracks[]`, `mainSource.subtitleTracks[]` | Track ids with language/title/default; `charset` is optional on subtitles |
| `additionalSources[]` | Extra files to mux in; the track id is always 0 |
| `trackOrder` | Optional `"sourceIndex:trackId"` CSV; see above |

### File selection and masks

Positional `FILE` arguments and `--exclude` patterns filter the file list in every mode, in both `mux` and
`inspect`. Unix shells expand `*.mkv` before the tool sees it, but `cmd.exe` passes the literal through,
so **globs are expanded internally** against the bare file name. A pattern that names an existing file is
matched **literally** instead — otherwise a file called `Odd[1].mkv` could not be selected at all, since
as a glob it also matches `Odd1.mkv`. Getting this wrong passes a Linux-only CI and fails on Windows. The
file list is sorted by name, so batches process predictably.

`mux` walks the mask result *before* the extension rule, because it reports what it passes over
(`*** Skipping notes.txt`) and needs to distinguish "nothing matched at all" from "nothing matched is
media" — two different mistakes, two different messages.

### Probing

**`mkvmerge -J` exits 0 on a file it cannot read**, signalling failure through `container.recognized` and
`container.supported` instead. `probeFile` checks those; trusting the exit code would let a corrupt file
into the comparison as a file with zero tracks, which reads as "every track is absent here" and poisons
the whole report. `probeFile` also discards stderr explicitly, since a chatty mkvmerge could otherwise
fill the pipe buffer while nothing drains it. There is **no timeout, on purpose**: a slow probe is normal
here — a NAS spinning up, a VPN link, a temporarily flaky share — and a timeout would turn ordinary
slowness into a failure.

Probe output is mapped into typed records at parse time, which retires by construction the Groovy trap
where a map's `properties` key resolved to the bean properties of the map object itself. Do not pass raw
maps around.

### The consistency check

Compares track structure across the batch. It works in **two layers**, which is the key design decision
and came out of a real mixed-layout season. First, files are grouped by **layout** — the type at each id,
plus the sorted set of external slot keys — printed largest group first; a per-id comparison alone put the
same shifted file at three different ids and was unreadable. Then, within each group, the **values** at
each id are compared (codec, language, name, default, forced), one row per distinct value. Grouping ranks
by population and never anchors on the first file.

- The video track's name is nulled *at construction* so it cannot enter a group key — it carries the
  episode name and would report every file as deviant — but the raw value rides alongside and is shown:
  the shared title when the files agree, `(per file)` when they do not, rather than presenting one file's
  title as the group's. Showing it never makes it a finding.
- `-` is the one glyph for "nothing here": an unnamed track, an absent language, a video row whose files
  carry no title.
- **Every group names its files.** The largest group used to go unnamed on the grounds that the majority
  is the norm; that was right when the report only hunted outliers, and wrong once the groups became "your
  muxing passes", where the first is as much an answer as the rest. No `<-` marker on it — that means
  "these rows deviate", a different question.
- Membership prints as **episode ranges** where the names allow it, anchored on an `SxxEyy` token or
  otherwise on the batch's longest common prefix with trailing digits trimmed off. The trim is what stops
  10-19 collapsing to 0-9, and what preserves 01-09's padding. This numbering is **display only**: it is
  batch-relative, so it can never answer "which episode is this file", and nothing that renames or
  resolves `${episodeNum}` may use it.
- Blocking classification: a layout outlier blocks when it changes the type at a selected id or drops one;
  a value discrepancy blocks when the id is selected and not every track of that type is copied.
  `findDuplicates` flags only genuinely ambiguous same-language tracks (type, language, codec *and* name
  all equal), since id selection cannot tell those apart.
- File lists print one name per line, ASCII only — this output reaches Windows consoles on legacy
  codepages — and the truncation limit has to be clamped to the list size, because verbose mode passes
  `Int.MAX_VALUE` and a naive `take` would allocate a two-billion-element array.

**External files are slots in the layout, not a section of their own**, because they are part of a muxing
pass: episodes with identical tracks but different dubs available are different jobs, and the grouping
says so. The slot key is `label/typeClass/extension`, and the extension is in the key because one variant
can hand a single episode two files of the same kind (`.ass` *and* `.srt` for E01, only `.ass` for E02) —
keyed on the kind alone they collide, the second silently overwrites the first, and two episodes come out
as one pass. External differences are never blocking (nothing selects an external file by id) but they do
split groups, which is the point.

**A value that can reach a group key is data; everything said *about* that value is presentation.** The
`?` an external row falls back to for a missing type or codec is composed in `core`, because it enters a
signature and the grouping must have seen it. The `-` for an absent language and the `rus?` marking an
inferred one are the renderer's: the model carries the bare `rus` with provenance in `guessed`, so a
guessed `rus` and a tagged `rus` compare **equal**, which is what stops a half-tagged dub directory
reading as two values and producing a "language differs" finding about ten files that are all Russian.
When a merged group's single row has to speak for members that disagree about provenance, it prefers a
member that *read* the value over one that inferred it — so the marker means "nothing here confirmed
this", and the row does not depend on file order.

### External-file discovery

Discovery is what `inspect` reports and `rename` renames by, which is exactly why both use one engine: a
drifted copy would rename files that inspection never showed. It **probes nothing** — matching is pure
name work, which is what keeps coverage free on a network share.

Three rules are load-bearing:

1. **Longest-prefix-wins** on name matching, or `Show - S01E01 - Title 2.srt` gets read as `…Title.mkv`
   plus the suffix `" 2"` whenever both files exist.
2. **An episode-number match requires a unique claimant.** Two main files for one episode makes the match
   ambiguous, and ambiguous means unmatched, never guessed.
3. **Variant identity is `(leaf directory, raw suffix)`** with same-named leaves merged, which is what
   turns `Rus sound/[MC-Ent]` + `Rus subs/[MC-Ent]` into one dub group. The merge is undone automatically
   when one episode would end up with two files of the same kind from different directories. Suffixes are
   matched **raw** and only trimmed for display: trimming for identity would fuse `[x]` and `(x)`, and
   renaming needs the original bytes.

The walk is recursive with dot-directories skipped, the caller's exclusions honoured by canonical path,
and a visited-path set against junction loops. `destinationDir` is excluded, because muxed output carries
its sources' base names and would otherwise come back as an external file of itself. The main-file scan
stays **flat**: a media file in a subdirectory is an extra (a menu, a trailer, a creditless opening),
never an episode.

Discovery runs once per process and **pre-mask on purpose** — matching against the masked list would dump
the rest of the season's dubs into "unmatched", the opposite of what a mask asks for. What the masks narrow
is what gets *displayed*.

Probed values win **field by field** over guesses: an `.mka` with a language but no track name shows the
real language and an empty name, never a guessed one. **`und` counts as missing**, since Matroska has no
other spelling for "untagged" and untagged dubs are the common case in exactly the releases this exists
for. Unprobed files report track id **0**, which is what mkvmerge calls their single track and therefore
what an `additionalSources` entry has to name.

### Language guessing

Spellings are **derived from CLDR at load time** rather than typed out: for each of a curated list of
codes, `Locale` supplies the three-letter code, the English name and the native name, which is what makes
`Русский` and `日本語` work as folder names. Matching is whole-word over Unicode letters, with multi-word
names tried as runs after single words.

The list is curated because obscure codes collide with ordinary English words (`new` is Newari, `sun`
Sundanese), and the bare two-letter form is withheld for codes that are ordinary words themselves — `No
subs` must not read as Norwegian, `UK BluRay` must not read as Ukrainian. Only the two-letter form is
withheld: the three-letter code and both names still match, so an entry costs almost nothing while a false
positive is a wrong language in a report used to write a config. That withholding table is consulted
**only inside the curated loop**, so an entry for a code that is never guessed at is dead weight reading
as protection it does not give; add the two together.

**CLDR gives the citation form only**, which is the guesser's real limit — not the token list. A native
name arrives as masculine nominative singular (`русский`), so a folder whose adjective agrees with its noun
does not match: `Русская озвучка` and `Русские субтитры` are both Russian and both miss, and every
language with adjective agreement has the same shape. The result is a `-` rather than a wrong answer,
which is the intended failure: declining to guess costs the reader nothing they had, while a confident
wrong `rus` in a report used to write a config costs them a season. Stem matching would catch it and is
deliberately not done — it reintroduces exactly the substring false positives the whole-word rule exists
to prevent.

### Substitution

Every templated config value — `general.title`, the three kinds of track `title`, and
`additionalSources[].file` — goes through one engine, the `${fileName}` placeholder in companion paths
included. Keep it that way: resolution done inline at a use site is a second implementation that will
drift from the validated variable set.

Validation is **two-stage, and the split matters**:

- **Stage one is config-static and fatal (exit 2)** in `mux`, running in every mode before anything is
  probed: an unknown variable name, a track variable in a file-scope field, a malformed body (caught by
  scanning with a deliberately looser pattern, so it cannot survive as a literal), or a `language` with no
  display name. A typo would otherwise be stamped into the track names of a whole season. The same
  diagnosis is a *warning* in `inspect`, which is why validation only diagnoses and each caller decides.
- **Stage two is per-file and drops** (`--strict` aborts): a valid variable with no data for one episode.
  That is data-shaped — TheMovieDB missing episode 25, a stray un-renamed file — and it matches the
  companion pre-flight's philosophy, which it sits beside. Both run before the output directory is
  created, so a fully blocked batch leaves nothing behind.

`${codec}` keys on `properties.codec_id`, **not** on mkvmerge's display string: the display string is not
stable across versions (v99 reports `AVC/H.264/MPEG-4p10` where older releases order the components
differently) and CI runs two mkvmerge versions, so a display-keyed map would resolve differently per leg.
The second tier is a small display-string map, needed because a raw non-Matroska companion has no
`codec_id` at all; the third is the raw display string, so unmapped codecs degrade rather than break.
Probing for `${codec}` is gated on the config actually using it and shares the batch's probe cache, so a
run without it costs no extra subprocesses.

`${languageName}`/`${languageNative}` come from CLDR via `Locale`, keyed by both the two-letter codes
`config.yaml` uses and the three-letter codes Matroska carries, plus the ISO 639-2/B bibliographic codes
that differ from /T (`ger`, `fre`, `dut`, …). Native names are upper-cased with the locale's own rules,
since many languages spell their own name in lower case.

The check report prints templates **unresolved** on purpose: it is batch-level and cannot resolve a
per-file variable, and its job there is to identify which config entry a finding refers to.

### `mux`

Discovers files, builds an `mkvmerge` command per file, and runs them, continuing past failures. The
pre-flights, in order: stage-one template validation (fatal), the episode-metadata load (fatal on any
problem), the consistency check (`Pre-flight check`, warn-only unless `--strict`), stage-two substitution
drops, and the companion pre-flight — the last two report and drop rather than aborting, because those
episodes would have failed in mkvmerge anyway and a partially released dub is a normal situation.

`--strict` stops the batch by *returning* an abort from the core rather than exiting from inside it; the
command turns that into exit 2. The two aborts are distinct types because they are reached at different
moments — one before a file has been read, one after the whole batch has been probed — and each says what
it found.

Three config fields that were once dereferenced unconditionally are now refused or omitted rather than
producing `null` in a command line: a missing `destinationDir` is a clean exit-2 error, a main-source
track with no `id` is refused by config path, and a genuinely optional `videoTrack` field is *omitted* so
mkvmerge keeps whatever the source carries. A **declared but empty** `title:` still emits
`--track-name <id>:`, which clears the name deliberately.

mkvmerge's own output is inherited rather than pumped through a reader, so its in-place progress line works
as mkvmerge intended.

### `inspect`

Everything that reports rather than muxes, and **nothing about a config can stop it**. The config may be
absent: extensions fall back to defaults, mkvmerge to PATH auto-detection, selections to empty. Missing,
empty, malformed, parsed-but-not-a-mapping, or valid with a template typo — each is counted, reported as a
warning, and the run continues.

Mode rule: `wantCheck = checkOnly || checkVerbose || !identifyOnly`. A bare run checks, `--identify` alone
identifies, naming both runs both off one scan — `--identify` and the check share a single probe per file,
so combining them does not double the subprocesses.

`--identify` also lists configured sources, resolving each `additionalSources[].file` for that episode and
printing the resolved path plus a probed sub-table. Never fatal: a source that is not there prints
`(not found)`, because `--identify` describes what exists rather than asserting it. Per-episode blocks are
grouped **by variant, not by file**, and everything on the page shares one column grid at a two-space
indent, so the columns line up straight down the report.

An empty batch returns before the `--strict` gate, and that condition is explicit in the code rather than
an accident of control flow.

### `rename` and `--external`

Renames to the canonical `Show - SxxEyy - Title[suffix].ext`, and the whole batch is checked before
anything moves: any file with no `SxxEyy`, no matching title, an existing target or a colliding target
means every problem is listed and **nothing is touched**. That matters because renaming removes the
`SxxEyy` that ties a file to its episode, so a rename that failed halfway would have to be untangled by
hand.

`--external` renames the external files belonging to each episode, wherever they live, and is off by
default. The order is what makes it work: **discovery runs before the plan is built**, since its answer
decides which files the ordinary pass must leave alone. A name match in the media directory is claimed by
the external rule rather than the legacy one, which is strictly better there too — the legacy suffix rule
keeps only a trailing `[...]`, so `Show.S01E01.rus.srt` would lose its `.rus` and collide with its own
English sibling. Episode-number matches are reported and skipped: with no name relation there is no "same
suffix" to preserve.

The new name is the main file's new base name plus the file's **own suffix, verbatim**, and its own
extension; the directory never changes, because the directory *is* the variant's identity. Two invariants
stretch across the tree rather than the directory: the duplicate key is `(parent directory, new name)`,
since two files in different directories renaming to the same name is not a collision; and the
refuse-all-on-any-problem rule covers external targets too, so one taken name anywhere aborts the whole
batch, main files included.

Characters a file name cannot hold (`\ / : * ? " < > |`) and trailing dots and spaces are dropped here, on
every platform rather than only on Windows, so one title produces one file name everywhere.

### `to-utf8`

Converts `.srt`/`.ass`/`.ssa`/`.vtt` **in place**, and it is safe to point at a directory more than once:

- Input that is already UTF-8 is skipped — by BOM or by a clean strict decode, which also covers pure
  ASCII. Double-converting is precisely how a previously fixed file gets ruined.
- Decoding **reports** malformed input rather than replacing it, because Java's default decoder silently
  substitutes and a wrong `--encoding` would otherwise produce mojibake that looks like success.
- UTF-16 is refused outright: every byte of it maps to something in a single-byte charset, so strict
  decoding alone would not catch it.
- `.sub` is excluded on purpose — the extension is ambiguous between MicroDVD text and the binary half of
  a VobSub pair, and rewriting the binary one would destroy it.
- Content is decoded and re-encoded **whole**, not line by line, so CRLF survives.

### `propedit` and `filename-to-title`

`propedit` passes every argument to `mkvpropedit` **verbatim**, with the file name inserted first, so
anything mkvpropedit accepts works with no code change — options that look like `mkvtool`'s own included.
Passthrough survives picocli via `unmatchedOptionsArePositionalParams`, set on that subcommand in one
place; the command declares one catch-all parameter list and *no* options, not even `--color`. `-h`/
`--help` is intercepted only when it is the sole argument.

Both commands reconstruct the target as `<base>.mkv`, which lower-cases the extension — a latent quirk,
reproduced deliberately, that would matter on a case-sensitive filesystem holding `Show.MKV`.

### `fetch-episodes`

The API key resolves as `--api-key`, then `apikey.txt` in the current directory, then
`~/.mkvtool/apikey.txt` (`%USERPROFILE%\.mkvtool` on Windows). TheMovieDB answers an untranslated field
with an empty string rather than falling back on its own, so a partially translated season is topped up
from `en-US` and the run says when it did that. Failures print TheMovieDB's own message. A hidden
`--base-url` points the fetcher at a stub server, which is how the command is tested offline.

## Kotlin-era traps

- **Groovy's `?:` is not Kotlin's `?:`.** Groovy elvis falls through on any *falsy* value — an empty
  string, `0`, an empty collection — while Kotlin's only catches `null`. Any ported `x ?: 'default'` over
  a String therefore means `x.orEmpty().ifEmpty { … }`, and every `if (someList)` means `isNotEmpty()`.
  This silently changed one check-report cell (an unnamed track rendered blank instead of `-`) and was
  caught by diffing rendered output, not by reading. Assume it is present wherever old logic is being
  reproduced.
- **Model types store only independent state.** Anything a data class can compute from its own fields is a
  computed `val`, so it cannot come to disagree with what it describes, and the parameter list stays about
  decisions rather than their consequences. One caveat before converting a field: the stored list may be
  in a *different order* than the one the value was originally computed from, so only order-independent
  derivations may move.
- **Locale-sensitive operations are pinned to `Locale.ROOT`** — number formatting for episode padding,
  lower-casing of base names and extensions. On a JVM whose default locale carries a non-Latin numbering
  system, the default would put non-ASCII digits into keys that are then joined against ASCII digits
  parsed out of a file name, and every lookup would miss.
- **Charset detection cannot rescue legacy single-byte input.** JEP 400 made the JVM default UTF-8 on
  every platform, and the detection utility only ever answers UTF-8 or the default, so a hand-typed
  windows-1251 `episodes.txt` is not detectable. That is `to-utf8`'s job. The fallback is a parameter, so
  a call site can override it.

## Architecture and workflow

The commands form a sequential pipeline:

```
TheMovieDB API
  └─ fetch-episodes → episodes.yaml + episodes.txt
       └─ rename    → renamed files (Show - SxxEyy - Title.ext)
            ├─ inspect (reports only; what you read to write config.yaml)
            └─ mux (+ config.yaml, + episodes.yaml for ${...} titles)
                 → mkvmerge → output MKV in destinationDir/
                 └─ post-processing:
                      filename-to-title, propedit, to-utf8, fix-srt, find-unused-fonts
```

### The manual workflow this automates

The tool is an incremental automation of a process the author had been doing by hand for years. Knowing
the whole of it explains decisions that look arbitrary from the code alone, and shows which steps are
still manual — that is where the remaining work is.

| # | Manual step | Automated by |
|---|---|---|
| 1 | Review the main files' tracks (mkvmerge, or a GUI) | `inspect --identify` |
| 2 | Decide which internal and external tracks to keep | `config.yaml` — a human decision; the tool only records it |
| 3 | Copy everything into one working directory, **flat** | nothing yet |
| 4 | Bulk-rename every file to bare `SxxEyy[suffix].ext` | nothing yet — a file manager's counter, or by hand |
| 5 | Fetch episode titles, then rename **all** files (mains *and* companions) | `fetch-episodes` → `rename` |
| 6 | Separate files into groups of identical track structure | `inspect` *reports* the groups; the split is still manual |
| 7 | Mux each group with its own track settings | `mux`, one `config.yaml` per group |

Consequences worth knowing before changing anything:

- **Step 4 is why `rename` does not need to parse exotic names.** By the time it runs, every file is
  already `SxxEyy[suffix].ext`. A release like `[Salender-Raws] Hellsing OVA - 05 (…)` becomes
  `S01E05[Salender-Raws].mka` first, which is why the strict `s(\d\d)\.?e(\d\d)` regex has never been a
  problem in practice, and why automating step 4 rather than loosening step 5 is the right fix.
- **Step 5 renames companions too**, which is why the extension list covers `.mka`/`.ass`/`.srt`/`.idx`/
  `.sub` and why a trailing `[...]` is preserved. The suffix identifies which dub or subtitle group a
  companion belongs to, and it has to survive the rename.
- **That pairing is what makes `${fileName}[Studio].mka` the canonical `additionalSources` pattern.**
  After step 5 a companion's name is the main file's name plus the suffix, so the placeholder resolves
  exactly. It is a consequence of steps 3-5, not a convention chosen for its own sake.
- **Step 7's "one config per group" is why the config is per-directory**, next to the media rather than
  next to the tool.
- **Step 2's "no one size fits all" is why this is a CLI plus config files rather than a GUI**: adapting
  the tool to the files is usually cheaper than adapting the files to the tool — though sometimes (step 4)
  adapting the files is unavoidable.

## Platform notes

Cross-platform: `mkvmerge` and `mkvpropedit` are resolved from PATH, with a fallback to the default
Windows install location (`C:\Program Files\MKVToolNix\`). The project originated on Windows, which shows
in a few places: the sample `mkvmergeExe` value in the example config uses a Windows path, episode names
are stripped of the characters invalid in Windows file names, and `to-utf8` defaults its source encoding
to windows-1251 (though `--encoding` accepts any charset). File lists in reports are ASCII because that
output reaches Windows consoles on legacy codepages. Native binaries are built for Windows x64, Linux x64,
macOS arm64 and macOS x64 — one CI leg each; CI runs the test suites on Linux. The x64 macOS binary needs
an Intel runner, because GraalVM does not cross-compile, and both macOS legs assert their architecture
twice: on the toolchain before compiling and on the binary afterwards, since an arm64 build published
under an x64 name is worse than a missing asset.

## The Groovy scripts (v1, frozen)

The nine scripts under `src/`, their shared code in `src/lib/`, and the `bin/` wrapper pairs are the
previous generation. They are **frozen**: never modify them, and never break their CI legs. They stay
until they are deleted, one release after v2.0.0.

Their *mechanics* are deliberately not documented here — the closures-instead-of-methods rule, the
`evaluate()`-by-absolute-path loading, the no-imports rule that shaped every helper's API, the
`@GrabConfig` fragility across Groovy versions, the Groovy `properties` trap. Each was the correct
solution inside the script model, and each is now needed only to *read* those files rather than to change
anything. They go out with the scripts, and so does this section.

What that era produced and the current code still embodies is the part worth keeping:

- **The config system exists because in-place editing was destructive.** Track selection was originally
  done by editing the mkvmerge command line inside the script, once per group. The script was not under
  version control at the time, so a botched edit destroyed the working invocation with nothing to recover
  it from — which happened more than once. Worth knowing before proposing anything that moves
  configuration back into code.
- **The config lives next to the media** because step 7 needs one config per group, and a season's
  decisions should outlive any version of the tool.
- **`inspect` and `mux` are separate commands** because a config is optional for reporting and required
  for muxing, and one script trying to be both was the confusing part.
- **`${fileName}` and rename's verbatim suffix preservation are one mechanism**, not two features: a
  companion is bound to its main file by *name*, so the file names had to be mutated until that was true.
  That coupling is a weakness rather than a design goal, and replacing it with matchers declared in the
  config is planned work.
